## CI layout

The `Rust React ordinary core` workflow splits its checks into parallel jobs:
`source` (publication allowlist, generated contracts, fmt, clippy, the four
named healthy examples and the Lantern healthy read; on macOS also the binary,
and the React app when the frontend lane is selected; on Linux also the
`healthy-agent-stock` example and the network-router flow), `backend unit
tests`, `frontend checks`, and three `loopback flows` shards that each build the
binary and the React app. The
[command inventory](#ordinary-ci-command-inventory) below lists every command.
CI builds use `CARGO_PROFILE_DEV_DEBUG=0`. Only main pushes save caches; the
Cargo cache holds compiled dependencies keyed by `Cargo.lock` and the toolchain.
Locally, `node tools/rust-integration/check-source.mjs` still runs everything;
the Linux `source` job passes `--skip-binary --skip-frontend` because other
jobs build those.

The `Ordinary synthetic core` workflow also runs the synthetic HomeBox quantity
seed report tests with the runner's `python3` (stdlib only, no install):

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/homebox-quantity-seed-report -p test_report.py -v
```

It also checks the NAS deploy tool against temp folders and a fake service,
without launchd, network access or real data:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/deploy-nas -p 'test_*.py'
```

and the nightly backup script, including its content-addressed model store,
against temp folders and a fake iCloud helper:


The checker uses the Python 3.9+ standard library, reads repository files only
and starts no subprocess or network connection. It reads the small workflow YAML
subset these files use and refuses tabs, anchors, aliases, quoted run commands,
unnamed run steps, workflow, job and run-step keys it does not read (such as
`defaults` or `container`) and other forms outside it. It fails when a run step
has no manifest row or a row has no step; when a command, condition, step `id`
(which later conditions read as `steps.<id>.outputs`), step env or option (`shell`, `working-directory`, `continue-on-error`, `timeout-minutes`),
trigger, workflow or job env, job selection, `needs` or listed file differs; when
a job's run steps are in a different order from their manifest rows; when a run
step's condition, env or command reads `steps.<id>` before any earlier step
(run or `uses:`) in its job has that id; when
a recorded case count differs (unittest methods,
top-level `test(` calls, `run-healthy.mjs` list entries, bridge case choices or
Cargo `--skip` flags); when a recorded prose claim or toolchain pin is gone; or
when the table below is stale. It does not compare `uses:` steps or their

synthetic cases in
`tools/ci/test_check_lanes.py` use temporary folders only and run in the
existing `unittest discover -s tools/ci -p 'test_*.py'` step. After changing the
manifest, regenerate the table:

```sh
python3 -B -I tools/ci/check_lanes.py --write
```

A passing check shows only that the manifest, this table and the workflow text
agree. It runs none of the listed commands and is not evidence that they pass;
hosted step logs remain the execution record.

## Generated capture original and draft receipt checks

The existing `run-healthy.mjs` SOURCE list adds these twelve exact commands,
one process per command, using Node 26.10.0 and unchanged locked frontend
dependencies. Inspect `foreground.mjs`, `combined-host.mjs`, their generated
fixtures and the imported client/controller/receipt validator before execution.

```sh
node frontend/capture-evidence-tests/selection.mjs --case selection-cancel-reselect
node frontend/capture-evidence-tests/foreground.mjs stale-target-preparation
node frontend/capture-evidence-tests/foreground.mjs one-shot-originals
node frontend/capture-evidence-tests/foreground.mjs original-offer-reused
node frontend/capture-evidence-tests/foreground.mjs original-offer-digest-mismatch

node frontend/capture-drafts-tests/combined-host.mjs --case existing-original-receipt-commit
node frontend/capture-drafts-tests/combined-host.mjs --case receipt-record-closure-keeps-original
node frontend/capture-drafts-tests/combined-host.mjs --case cleanup-failure-known-commit
node frontend/capture-drafts-tests/combined-host.mjs --case reused-receipt-object-keeps-unknown
```

The selection case holds File reads at the header and text boundaries, aborts
the old caller and selects a replacement and then the same original again; it
mounts no picker. The stale-target case holds the final fresh admission read,
then retires the binding or session or cancels, and requires that a late reply
cannot revive preparation before a fresh generation selects the same bytes
without sending. The foreground baseline checks exact multipart bytes and one fake POST for
baseline/progressive JPEG, PNG, PDF and text. `original-offer-reused` adds the
production resolver's asset GET / HEAD / asset GET over two-record receipts
for the same five originals. The other three offer cases withhold the offer
for a wrong digest at equal MIME/size, a revision change after HEAD or a missing
asset; the validated commit stays retained with one POST. Metadata comparisons
are neither an atomic lease nor actual original-download byte measurements.

The two draft positives cover created-asset and existing-original receipts,
durable-marker ordering in the deterministic store and local cleanup. The
record-closure case supplies exactly eighteen schema-valid mismatches and
requires zero cleanup, retained exact bytes, unknown inspection and no
redispatch. The two cleanup cases distinguish a correlated commit with failed
local deletion from reuse of an earlier receipt for a separate attempt.

These checks use generated Files, fake exchanges/owners and a deterministic
memory store; the draft harness traps global fetch. No DOM, listener, native
service, real IndexedDB, credentials or household input is involved. The
foreground harness temporarily supplies only a fictional window origin.
Neither harness mounts React or downloads an original from a native server.
Registration is not an execution result, browser/device acceptance, native
custody/recovery proof or permission to retry an unknown result.

This is a finite exception for the named selection, stale-target and
receipt/original-offer cases. Other selection, byte/receipt mismatch, lifecycle, quota, expiry,
cross-tab and controller regression cases remain separately selected. The
native UI harness and browser-cases runner remain outside this list. The full
controller regression file contains thirteen cases and is not selected here.
No new workflow or browser infrastructure is added.

pending-call release and the handshake/exit continuation race. Fake EventEmitters
and a controlled clock launch no child, browser, socket or service.

The media flow makes one `Browser.getVersion` request with a 60 s launch-only
budget before page/cookie work. It never retries or relaunches. Subsequent CDP
calls retain 15 s. Readiness is a correlated, valid version response from a
still-live pipe, not the spawn event or successful write alone. Startup receipts
contain only timing, counts and process/pipe state; no CDP payloads or stderr.
This bounded wait accommodates delay without diagnosing its cause. Framing,
child exits and pipe/write failures fail immediately rather than waiting out
that budget. Other copied loopback flows are unchanged by this increment.

Media teardown reuses the close-aware owned-child helper: 2 s graceful, 2 s TERM
and 3 s KILL, with no broad process discovery or signals. Failed startup does
not attempt another handshake or protocol close. Removal waits for browser and
service closure; uncertain closure retains synthetic scratch. Cleanup failures
are additional diagnostics when a primary assertion failed, and fail an otherwise
successful case. The existing CI job limit and application assertions are unchanged.
Registration is not an execution result or device acceptance.

## Real-browser offline launch

`frontend/lantern-tests/offline-launch-browser.mjs` serves the built `dist/` on
an owned loopback listener, opens `/saved/index.html` once online so the Saved
and root workers install, then reopens `/` without a network and times how long
the Saved shell takes to appear. It uses public generated build output and, in
`live-launch`, a generated Atlas and a waiting synthetic outbox record.

```sh
node frontend/lantern-tests/offline-launch-browser.mjs --case offline-launch
node frontend/lantern-tests/offline-launch-browser.mjs --case hung-network
node frontend/lantern-tests/offline-launch-browser.mjs --case live-launch
```

`offline-launch` closes the listener (connection refused) and must show the
shell within 2 s with no network bytes; it is in the healthy suite.
`hung-network` keeps the listener open but never answers `/`, as on a captive
portal or a weak signal. It must show the shell within 3 s; the root worker
hands a silent navigation to Saved after 2 s. The listener may answer a
worker-script update check (`/offline-entry-worker.js`,
`/saved/service-worker.js`) during the reopen; any other served path fails the
case. `live-launch` is `offline-launch` with the live entry `/` opened online
instead of the Saved entry: the live app registers both workers after every
launch (no backend answers it here). That case seeds a generated Atlas and one
waiting edit through the production storage APIs, closes the application tab,
then opens a new tab offline. It checks the actual cached Atlas and waiting
count, unchanged full queue record, and absence of write dispatch. It does not
simulate a canonical session or claim an edit was accepted by a native backend.
All three cases remain in the existing healthy suite. Reconnect synchronization
through a canonical signed-in live session, iOS, installed-PWA and real content
remain separate acceptance. `unified-atlas-cache-healthy.mjs` checks the cached
copy's actor isolation and lifecycle without a browser.

Offline browser teardown observes its owned child immediately after spawn.
It allows up to 2 s for protocol-requested closure, then 2 s after TERM and
3 s after KILL, always waiting for the child's close event rather than the
protocol acknowledgement or kill return value. A failed shutdown retains
the generated profile and fails the check. Only the fixture's own temporary
directory is removed, with at most five 100 ms retries for transient
ENOTEMPTY, EBUSY or EPERM; unrelated errors are not retried.

The already listed `offline-root-entry-healthy.mjs` case also exercises this
shutdown helper with fake child events and generated temporary directories:
delayed close after exit/ack, missing acknowledgement, TERM/KILL fallback,
already closed child, retained scratch on timeout, retry exhaustion and
successful bounded cleanup. It launches no browser or real child process.
The original test exception remains primary if shutdown or removal also fails;
all cleanup diagnostics are reported separately. When the test itself passed,
cleanup failure still fails the case. Combined-failure assertions use synthetic
errors and verify original identity, cleanup-only failure and ordered release.
Transport release stops listener acceptance, then enumerates the live owned socket
set after browser shutdown. Synthetic coverage adds a resource during fake-child
shutdown and verifies its release on both successful close and shutdown timeout.
These checks concern harness reliability, not offline application or device
acceptance.
